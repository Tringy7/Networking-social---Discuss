# Discuss UI redesign audit

**Phase 0 · 25 November 2026 · Awaiting approval**

Discuss already has a recognizable visual foundation. Nunito Sans, a configurable orange accent, neutral light and dark surfaces, shared social navigation, and distinct authentication and administration layouts provide a common starting point. The highest-impact changes are to constrain the reading area, improve how appearance preferences reach content, and organize profile information around identity and activity.

This audit uses the actual frontend routes, components, CSS cascade, settings store, design documentation, and the text extracted from the supplied profile screenshot. The screenshot identifies the owner view and its current About fields. Exact visual proportions, computed layout, accessibility behavior and authenticated flows still require browser verification.

## Confirmed findings

| Priority | Finding and current implementation | Proposed change and expected improvement | Dependencies and risks |
| --- | --- | --- | --- |
| P0 | **Reading width grows on wide displays.** In [social.css](frontend/src/social.css#L278), the later `.route-content > div` rule replaces the earlier 1440 px cap with `max-width: none`. The 248 px navigation and 300–320 px rail leave a fluid reading column. Home and post detail already share `.feed-layout`, so a separate width mismatch between them is unconfirmed. | Center a shared social canvas around 1200 px, with a reading column around 720–820 px, a 300–320 px rail and a 24 px gap when room allows. Keep administrative tables and discovery layouts eligible for wider variants. This reduces long reading lines and aligns posts across routes. | Verify the actual wrapper in [PageTransition](frontend/src/components/layout/PageTransition.tsx), including reduced-motion mode. An overly broad selector could constrain settings, search, or tables. Measure before choosing a cap. |
| P1 | **Overlapping layout rules obscure the effective styles.** [social.css](frontend/src/social.css#L246) declares breakpoint-specific feed sizing and earlier card treatments. Later rules override the grid values, article chrome and post detail width, including two competing `!important` declarations for the latter. | Consolidate declarations after checking computed styles at each breakpoint. Preserve the current divider-based feed while bringing spacing onto existing tokens. This makes the cascade easier to change and reduces accidental regressions. | Coordinate with the canvas change. Check class usage and responsive states before deleting declarations. |
| P1 | **Appearance settings vary in coverage.** [useSettingsStore](frontend/src/store/useSettingsStore.ts#L165) sets root font-size and density classes. [social.css](frontend/src/social.css#L237) targets a small set of rows and excerpts for compact mode, while [postContent.css](frontend/src/components/post/postContent.css#L51) fixes Markdown type in pixels. Root font-size changes therefore bypass those fixed content sizes unless an explicit override exists. | Derive reading typography and selected spacing from existing relative tokens. Keep compact mode focused on list gaps and row padding so form controls remain usable. Verify both themes and all supported accent presets using their computed foreground and hover colors. | Review auth, admin, Markdown and settings separately. Relative sizes can cause wrapping in menus, tables and long Vietnamese labels. |
| P1 | **Profiles present a loaded count as an account statistic.** [UserProfilePage](frontend/src/pages/profile/UserProfilePage.tsx#L304) displays `userPosts.length`. The post store fetches pages and merges them into the working collection. The profile comments tab renders an unconditional empty view, and the public profile service supplies empty statistics. | Keep real reputation score and rank together. Present totals only where the existing data actually supplies them. Keep biography prominent, reduce repeated identity details and use compact rows for optional metadata. The owner’s add-bio action stays available. | Check [usePostStore](frontend/src/store/usePostStore.ts#L120) and [PublicUserProfileService](backend/src/main/java/com/discuss/discuss/service/user/PublicUserProfileService.java#L48). A placeholder statistic or first page count would misstate user activity. |
| P1 | **The home and detail context rail disappears at 1100 px and below.** The breakpoint in [social.css](frontend/src/social.css#L332) hides `.context-rail`, while the profile and community supporting sections already stack. | Inventory the content of [RightSidebar](frontend/src/components/layout/RightSidebar.tsx). Stack or otherwise surface useful contextual actions on narrow viewports if they lack another route. Verify the resulting reading and keyboard order. | Navigation already available elsewhere can remain in the existing mobile navigation. Stacking the full rail may add unnecessary scrolling. |
| P2 | **Attached images and inline images have different height limits.** [postContent.css](frontend/src/components/post/postContent.css#L62) allows inline Markdown images up to 640 px. Attached galleries already cap one image at 420 px and use 240–360 px for multi-image layouts. [PostBody](frontend/src/components/post/PostBody.tsx#L44) already exposes remaining attachments through the lightbox. | Measure portrait and inline images in the feed. Apply a feed-specific limit where images crowd out adjacent context, while keeping a more generous detail view and access to original images. Preserve the current gallery structure unless visual testing reveals a specific issue. | Verify single, mixed-ratio and seven-plus image cases, mobile height, keyboard navigation and direct image links. Use presentation CSS so uploaded images remain intact. |
| P2 | **Banner ratio changes with the viewport.** [social.css](frontend/src/social.css#L420) uses an 8:1 banner capped at 140 px, switches to 6:1 with a 90 px cap on mobile, and uses `object-fit: cover`. This can remove more of a 3:1 image from the visible frame. | Review banner composition after the width change. Test the proposed 150–180 px desktop range before choosing whether to increase the current height. Align the avatar, name and actions across profiles and communities. | Compare actual uploaded crops and the fallback. Full-width taller banners can push activity further down the page. Preserve the upload and crop workflows. |
| P2 | **Administration documentation differs from active routes.** [ADMIN_UI.md](frontend/ADMIN_UI.md) lists a comments page. [adminRoutes.jsx](frontend/src/routes/adminRoutes.jsx) exposes activity logs and reputation settings and has no comments route. | Update design documentation after the UI changes using the active route list. Keep admin tables dense and verify filters, statuses, row actions and dialogs inside the dedicated admin shell. | A documentation discrepancy does not establish a missing product feature. Use supported modules for the review. |

### Privacy contract follow-up

The public mapping in [services/index.ts](frontend/src/services/index.ts#L169) supplies an empty email value and sets `showPostsOnProfile` to `true` locally. The UI therefore lacks an explicit public visibility signal for posts. This finding alone does not establish that the post API returns private content. The public date mapper applies `showDateOfBirth` to the full date and has no separate birth-year branch in [PublicUserProfileService](backend/src/main/java/com/discuss/discuss/service/user/PublicUserProfileService.java#L53). Confirm which controls the product exposes and verify the responses as a visitor before changing presentation. Keep email owner-only and treat any discrepancy in server enforcement as a separate backend issue.

## Implementation order after approval

1. **Foundation** — Establish the shared width constraint, resolve competing rules, and validate theme, font size and compact density before editing individual screens.
2. **Shared controls and navigation** — Audit buttons, fields, tabs, menus, the header and both navigation layouts. Update shared primitives first.
3. **Core social screens** — Apply the width and typography changes to feed, detail, comments, profile and community. Verify galleries and the About section with real data.
4. **Secondary screens** — Review discovery, search, notifications, composer, settings, auth and community moderation using the revised foundation.
5. **Administration** — Verify existing tables, filters, statuses, dialogs and role-gated actions within the admin layout.
6. **Verification and documentation** — Record the measured results, update [DESIGN_README.md](DESIGN_README.md), the repository’s current design reference, and write `UI_REDESIGN_REPORT.md` based on the implemented changes.

## Verification checklist

| Check | Cases |
| --- | --- |
| Layout | 360, 390, 768, 1024, 1280, 1440, 1920 and 2560 px. Compare feed, post, profile and community edges. Check both sides of each breakpoint, navigation handoff, no page-level horizontal overflow and dialogs in short viewports. |
| Theme and accessibility | Light, dark and system modes, every accent preset, all font sizes, both densities and reduced motion. Check normal text contrast of at least 4.5:1 and large text at least 3:1 where applicable. Exercise keyboard navigation, focus visibility, Escape, labels and non-color status cues. |
| Content and state | Long Vietnamese names, long titles, code, wide tables, empty/effective error states, loading, inline images and galleries with one, two, three, four and more than six photos. |
| Account and permissions | Signed-out, owner, visitor, member, moderator and admin views. Smoke-check auth, profile edits, media uploads, post creation, voting, comments, saves, notifications, search, community membership and moderation using existing routes. |
| Tooling | Run the existing frontend build and lint commands before and after UI changes. Record observed failures and unverified cases. |

**Baseline:** The frontend production build passed and emitted a bundle-size warning for a chunk above 500 kB. The existing lint command failed on generated build assets and existing source findings, including `no-control-regex` in `errorTranslation.js`. The responsive matrix, logged-in workflows and screen-reader behavior remain unverified.
